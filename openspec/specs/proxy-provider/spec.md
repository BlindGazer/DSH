# Прокси для провайдеров моделей

## Purpose

Плагин управляет профилями прокси и направляет сетевые запросы серверной части DSH по адресу назначения. Привязка профиля в настройках провайдера определяет адреса для маршрутизации, но не дает каждому провайдеру отдельный маршрут к общему адресу.

## Requirements

### Requirement: Управление профилями и проверка соединения

Плагин MUST позволять создавать, редактировать и удалять именованные профили HTTP, HTTPS и SOCKS5 с адресом, портом и необязательной аутентификацией. Пользователь MUST иметь возможность проверить соединение по тестовому адресу через выбранный профиль без назначения этого профиля провайдеру. Проверка MUST сообщать результат и задержку при успехе либо причину отказа.

#### Scenario: Проверка нового профиля
- **WHEN** пользователь проверяет соединение по профилю, не назначенному ни одному провайдеру, и тестовый адрес отвечает успешно через этот прокси
- **THEN** плагин показывает успешный результат и задержку, не меняя привязки провайдеров

#### Scenario: Прокси отклоняет учетные данные
- **WHEN** HTTP-прокси отвечает кодом 407 на проверочный запрос через профиль
- **THEN** плагин показывает отказ проверки, а не успешное прямое подключение

### Requirement: Выбор профиля по адресу назначения

Плагин MUST предлагать выбор профиля или прямого подключения для обнаруженных провайдеров и пересчитывать маршруты при изменении привязок. Для серверных запросов через `fetch` плагин MUST выбирать маршрут по целевому имени хоста с портом, если для этого адреса есть точное совпадение, иначе по имени хоста. Запрос без подходящего маршрута и запрос с явно заданным транспортом MUST передаваться нижележащему `fetch` без выбора профиля плагином.

#### Scenario: Разные порты одного хоста
- **WHEN** адреса двух провайдеров отличаются нестандартными портами и им назначены разные профили
- **THEN** серверный запрос к каждому из этих адресов использует профиль для его порта

#### Scenario: Прямое подключение без общего маршрута
- **WHEN** пользователь сбрасывает привязку провайдера на прямое подключение, а другими привязками маршрут для его адреса не задан
- **THEN** серверный запрос к адресу передается нижележащему `fetch` без профиля плагина

#### Scenario: Запрос со своим транспортом
- **WHEN** серверный запрос к адресу с настроенным маршрутом явно передает собственный диспетчер (`dispatcher`)
- **THEN** плагин передает запрос нижележащему `fetch`, не заменяя диспетчер

#### Scenario: Ошибка назначенного прокси
- **WHEN** для серверного запроса выбран профиль, но назначенный прокси не устанавливает соединение
- **THEN** запрос завершается ошибкой без прямого повтора со стороны плагина

### Requirement: Один маршрут для общего адреса

Если несколько обнаруженных провайдеров используют один адрес с различающимися настройками маршрута, плагин MUST показывать конфликт и применять первый назначенный действующий профиль в порядке построения таблицы маршрутов. Идентификатор провайдера MUST NOT определять транспорт отдельного запроса к общему адресу.

#### Scenario: Два профиля для общего адреса
- **WHEN** два провайдера используют один и тот же адрес назначения и им назначены профили с различными настройками
- **THEN** плагин показывает конфликт и применяемый профиль, а запросы обоих провайдеров к этому адресу используют один маршрут через первый действующий профиль

#### Scenario: Прямое подключение и прокси для общего адреса
- **WHEN** один провайдер оставлен без привязки, а другому провайдеру для того же адреса назначен профиль прокси
- **THEN** плагин показывает конфликт и использует назначенный профиль для обоих запросов к адресу

### Requirement: Хранение и перенос настроек без раскрытия учетных данных

Плагин MUST хранить учетные данные прокси зашифрованными и не возвращать их открытым текстом в клиентском состоянии настроек. Экспорт MUST исключать учетные данные по умолчанию; для включения учетных данных пользователь MUST задать пароль шифрования. При импорте плагин MUST позволять либо расшифровать данные по этому паролю, либо пропустить зашифрованные данные файла.

#### Scenario: Сохранение профиля с аутентификацией
- **WHEN** пользователь сохраняет профиль с учетными данными и повторно открывает настройки
- **THEN** серверное хранилище содержит зашифрованные учетные данные, а клиентское состояние не содержит введенных логина и пароля в открытом виде

#### Scenario: Обычный экспорт
- **WHEN** пользователь экспортирует настройки без включения учетных данных
- **THEN** экспорт содержит профили и привязки без учетных данных

#### Scenario: Перенос профиля с учетными данными
- **WHEN** пользователь экспортирует настройки с учетными данными и паролем шифрования, затем импортирует их в другом экземпляре плагина с тем же паролем
- **THEN** другой экземпляр восстанавливает учетные данные для использования профиля, не раскрывая их в клиентском состоянии

#### Scenario: Импорт без переноса учетных данных
- **WHEN** пользователь импортирует файл с зашифрованными учетными данными и выбирает пропустить их
- **THEN** плагин импортирует настройки профилей без расшифровки учетных данных из этого файла

### Requirement: Проверка сертификатов

Плагин MUST проверять сертификаты TLS по умолчанию. Пользователь может отключить проверку для отдельного профиля. Для HTTPS-прокси это отключает проверку сертификата самого прокси, а также сертификата HTTPS-адресата.

#### Scenario: Недействительный сертификат
- **WHEN** проверка включена и сертификат HTTPS-адресата или HTTPS-прокси недействителен
- **THEN** соединение отклоняется
