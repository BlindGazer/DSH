# Задачи

Условие начала реализации: изменение OpenSpec должно быть создано и явно утверждено пользователем до переноса файлов или изменения кода, включая пункт 1.2 и последующие пункты реализации. До утверждения допускается только аудит без изменения кода. Согласование отдельных правок плана не означает утверждения всего изменения; факт утверждения фиксируется в `memory.md`.

## 1. Аудит и перенос по слоям

- [x] 1.1 Выполнить аудит текущего содержимого локальной папки `D:\GIT\DSH\dsh-plugin-addir` как единственного источника переноса; зафиксировать исходную ревизию Git, состояние локальных незакоммиченных изменений, перечень переносимых файлов, включая необходимые исходные файлы, не добавленные в Git, и исключения. Сопоставить исходные модули, точки входа, тесты и зависимости с целевыми слоями `src/shared`, `src/host` и `src/client`; сверить компоненты, хуки, API и токены с экспортами `@kalex/dsh-core`. Проверка: составлена карта переноса именно локального содержимого, учтены локальные изменения, каждому модулю назначен слой и отмечены отсутствующие общие примитивы.
- [x] 1.2 Перенести файлы непосредственно из `D:\GIT\DSH\dsh-plugin-addir` в `packages/dsh-workspace-manager` по карте из пункта 1.1, сохранив локальные изменения исходного кода; не заменять источник клоном, опубликованным пакетом, версией с GitHub или экспортом только закоммиченной ревизии. Исключить `.git`, `node_modules`, генерируемые результаты сборки и локальные секреты; разложить модели, DTO, константы и проверки в `src/shared`, Cordis и Node.js службы в `src/host`, клиентские функции и компоненты в `src/client`. Исходную папку не изменять. Проверка: сверка с картой переноса подтверждает полноту переноса и сохранение локальных изменений с учетом адаптации, исходная папка не изменена, слои не импортируют запрещенные зависимости и в перенесенных файлах нет локальных секретов.
- [x] 1.3 Привести модели и код хоста к правилам TypeScript монорепозитория: TypeScript не ниже 7.0.2, строгие типы, неизменяемые данные, интерфейсы для форм объектов и отсутствие запрещенных небезопасных конструкций. Проверка: типизация host/shared проходит без подавлений ошибок и запрещенных конструкций.

## 2. Клиентский интерфейс и сборка

- [x] 2.1 Разложить клиентские модули по функциям, вынести запросы, состояние и преобразование данных из компонентов в хуки, оставить один компонент на файл; перенести пользовательские строки на английском и русском в `src/shared/constants/localizations`, а селекторы тестов в `src/shared/constants/testId.ts`. Проверка: компоненты и хуки соответствуют правилам фронтенда, строки и test id не дублируются.
- [x] 2.2 Использовать подходящие компоненты, хуки, контракты и токены из `@kalex/dsh-core` с импортом из исходников; при отсутствии требуемого общего UI-примитива добавить его в `dsh-core`, не создавать локальную замену. Перед изменением интерфейса загрузить навык `front-design-principles` и применять его требования ко всему клиентскому коду. Обновить стили на токены `--dsh-ui-*` и проверить темы, узкую панель и доступность по проверочному списку этого навыка. Проверка: отсутствуют дублирующие UI-примитивы, зафиксированы результаты каждого применимого пункта проверочного списка `front-design-principles`, а неприменимые пункты отмечены с причиной.
- [x] 2.3 На начало выполнения пункта определить последнюю стабильную версию React (не предварительную и не ниже 19.3), зафиксировать версию, дату и источник проверки в `memory.md`; согласовать React DOM и совместимые типы с выбранной версией и монорепозиторием. Проверить совместимость с внешним React runtime DSH; при отсутствии подтвержденной версии не объявлять runtime-совместимость доказанной и не включать отдельный React в клиентский пакет. Сопоставить клиентские подключения с актуальными декларациями Cordis Inspect и использовать только объявленные службы, слоты и общие модули; не полагаться на API старой версии DSH или недоступные клиентские пакеты. Заменить tsdown на фабрики `createDshHostViteConfig` и `createDshClientViteConfig` из `configs/vite.base.ts`, включить React Compiler через Oxc без Babel. Использовать `dshModuleLoaderPlugin`, сохранив host ESM, клиентский CJS/browser, внешний React runtime, classic module-loader wrapper, точки входа и декларации типов. Проверка: обе сборки создают ожидаемые файлы, клиентские подключения соответствуют live-контрактам Inspect, бандл не включает второй экземпляр React, а применимые проверки выпуска проходят.
- [x] 2.4 Переименовать пакет в `@kalex/dsh-workspace-manager`, обновить workspace-манифесты, зависимости, импорты и публикационные сведения, сохранив совместимые runtime-идентификаторы `addir`, API, инструментов, локализации, слотов и хранилища. Проверка: поиск не находит устаревшее имя кроме атрибуции исходного проекта, а тесты подтверждают совместимость данных и точек подключения.
