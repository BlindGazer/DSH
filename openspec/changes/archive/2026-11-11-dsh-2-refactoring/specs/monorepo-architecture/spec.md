# monorepo-architecture Specification

## Purpose

Определяет единую модульную структуру пакетов в монорепозитории, правила переиспользования общего кода через пакет `@kalex/dsh-core`, автоматизированный контроль качества и типизации кода, а также контекстное разграничение правил для агентов по областям разработки.

## ADDED Requirements

### Requirement: Единая структура пакетов и слоев в монорепозитории

Все пакеты репозитория MUST располагаться в каталоге `packages/` (`packages/dsh-core`, `packages/dsh-agents-router`, `packages/dsh-proxy-provider`) и использовать единообразную послойную организацию исходного кода с однонаправленными зависимостями от общих моделей к серверной и клиентской частям. Каждый файл MUST отвечать только за одну задачу: визуальные компоненты содержат только разметку, а управление состоянием и загрузка данных выносятся в отдельные хуки и сервисы.

#### Scenario: Размещение и изоляция слоев плагина

- **WHEN** разработчик или агент создает или изменяет код в пакетах плагинов внутри `packages/`
- **THEN** код разделен на общие контракты и константы (`src/shared/`), серверную логику (`src/host/`) и клиентский интерфейс (`src/client/` с выделением независимых функциональных модулей `features/`), причем серверная часть не зависит от клиентской, а функциональные модули не импортируют друг друга напрямую

#### Scenario: Разделение разметки компонента и логики состояния

- **WHEN** в клиентской части создается или изменяется интерактивный компонент
- **THEN** файл компонента содержит только описание пропсов и разметку, а работа с состоянием, запросами и подписками располагается в отдельном хуке соответствующего модуля

### Requirement: Прямое переиспользование общего пакета внутри репозитория и автономная сборка для публикации

Общие визуальные компоненты, система дизайна, хуки, локализация, модели и утилиты MUST находиться в пакете `@kalex/dsh-core` (`packages/dsh-core`). Пакет `@kalex/dsh-core` MUST иметь собственный цикл сборки, проверки типов и модульного тестирования для самостоятельной публикации, а пакеты `dsh-agents-router` и `dsh-proxy-provider` внутри репозитория MUST подключать `@kalex/dsh-core` напрямую через исходный код без установки внешнего пакета.

#### Scenario: Использование общих компонентов и утилит в плагинах внутри репозитория

- **WHEN** плагины `dsh-agents-router` и `dsh-proxy-provider` собираются или проверяются внутри монорепозитория
- **THEN** импорты из `@kalex/dsh-core` разрешаются напрямую в исходный код `packages/dsh-core/src` без необходимости публиковать или устанавливать внешний пакет

#### Scenario: Самостоятельная сборка и проверка общего пакета

- **WHEN** запускается сборка и тестирование пакета `@kalex/dsh-core`
- **THEN** пакет успешно проходит модульные тесты и формирует готовые файлы сборки и декларации типов для внешней публикации

### Requirement: Надежная проверка типов и автоматизированный контроль качества

Исходный и тестовый код MUST проходить статическую проверку типов. Нельзя использовать конструкции, подавляющие диагностику или маскирующие несовместимость типов. Внешние данные MUST проверяться до использования. Обязательные проверки MUST сообщать об ошибке ненулевым кодом завершения.

#### Scenario: Обнаружение ошибки типа

- **WHEN** в исходном или тестовом коде появляется ошибка TypeScript
- **THEN** штатная проверка проекта обнаруживает ее и завершается с ошибкой

#### Scenario: Ошибка инструмента проверки

- **WHEN** обязательный инструмент проверки отсутствует или сообщает об ошибке
- **THEN** штатная команда проверки завершается с ошибкой и указывает причину

#### Scenario: Автоматическое форматирование и исправление кода

- **WHEN** агент или разработчик запускает скрипт автоматического исправления и проверки проекта
- **THEN** инструмент автоматически приводит форматирование и сортировку импортов к стандарту проекта, проверяет правила компилятора React и строгую типизацию, после чего выводит только неисправимые автоматически ошибки

#### Scenario: Сборка клиентской части с компилятором React и минификацией Oxc

- **WHEN** выполняется сборка клиентской части плагина через Vite
- **THEN** сборка использует встроенную поддержку компилятора React и минификатор Oxc без использования Babel и формирует корректный бандл для загрузчика модулей DSH

### Requirement: Сохранение поведения независимых плагинов

Каждый плагин MUST сохранять пользовательские возможности и контракты интеграции при переносе и MUST проверяться отдельно от других пакетов.

#### Scenario: Проверка сохранения возможностей

- **WHEN** критические пользовательские сценарии сравниваются с исходным проектом
- **THEN** соответствующие проверки подтверждают сохранение поведения, интеграции и гарантий безопасности

#### Scenario: Независимая проверка пакета

- **WHEN** собирается или тестируется один плагин
- **THEN** результат не зависит от предварительной сборки другого плагина, кроме явно объявленных общих контрактов

### Requirement: Разграничение правил и навыков для агентов по областям

Правила и навыки для агентов в каталоге `agents/` MUST быть разделены по тематическим областям (общие правила, клиентский интерфейс и дизайн-система, серверная часть плагинов, тестирование, работа со спецификациями), чтобы при работе с конкретной областью автоматически подгружались только относящиеся к ней инструкции.

#### Scenario: Подгрузка правил при работе с конкретной областью кода

- **WHEN** агент работает с файлами клиентского интерфейса, серверной логики, тестов или спецификаций OpenSpec
- **THEN** конфигурация маршрутизации в `agents/dsh/agents-router.json` сопоставляет пути и ключевые слова с соответствующей областью и подключает только нужные правила без загрузки всего набора правил проекта
